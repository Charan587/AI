# Progress Log

Append-only, verbatim record. Every entry keeps the **actual** prediction read, the **actual** run output and the **actual** submitted code path — nothing summarized away, so any future session sees what happened rather than my recollection of it.

**Read this file at the start of every session** before writing a brief, notes or a review.

## Standing deliverables — do these every week, without being asked

1. **`week-NN/BRIEF.md`** — the week's question, the artifact due, the paper, the five weekday reps.
2. **`week-NN/NOTES.md`** — written *after* the Saturday prediction read, aimed at what it missed. **Derived, not asserted**: the concrete problem → why the obvious approach fails, *shown with a real trace or plot* → the derivation → a full dry run with real numbers generated by running code → only then the implementation → complexity/memory with the reasoning → the bug list. See `feedback_teaching_style` memory.
3. **`week-NN/REVIEW.md`** — verdict with real run output, 5-axis score, defects with probe traces, the ablation numbers, grill questions.
4. **`notes/<topic>.md`** — the durable note for that week's concept, same derived-not-asserted rule. This is the file he'll reread in two years.
5. **`PROGRESS.md`** — prediction read verbatim, score row, defect log, standing-weakness updates.

## Rules for me

- Prediction read is graded **before** any teaching, and logged verbatim. It is **not** folded into the 5-axis score.
- **A mid-week loop change applies to the NEXT week, never the current one.** (Carried over from the DSA track, learned the expensive way on day 3.)
- Never hand over the reference implementation before his version has run.
- Every claim I make in notes gets a number or a trace. If I catch myself writing "this helps training", I go generate the two loss curves instead.
- Weekend budget is a hard stop. Tired → stop, hand over the worked version to read when rested, carry the remainder to next week.
